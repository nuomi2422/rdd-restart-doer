# 第一批任务链运行与维护定位手册

配套：`第一批深审-20260930.md`。这是当前实现的地图及故障定位说明，非“全部功能已验收”声明。

## 1. 正常主链

```
用户goal
 → RddPlugin.beginPlanning（generation ticket）
 → RddStagePlanner：Stage-A阶段
 → bindCurrent：TaskChain + CompletedFactStore继承
 → Detector看见当前阶段unexpanded
 → RddGoalDriver.needExpansion（预算/冷却/inFlight）
 → RddDecomposer：Stage-B条件与body建议
 → PlanGuard过滤 + server/generation检查
 → TaskChain.expandCurrentPrimary
 → activateCurrentFromSnapshot
 → 执行脑读取当前任务与世界资产
 → find_tools披露 → ToolDispatcher → 宿主TaskSlot → core动作
 → Detector读取真实库存/世界条件
 → applyHardCodedResult → COMPLETED / AWAITING_SUPERVISOR
 → CONFIRM + recordStageFact → 下一阶段或全目标COMPLETED
```

两条入口不同：`rdd_submit`是显式单条件任务，不能拿它构造草率条件再据此评判自然长任务规划；Stage-A/Stage-B是完整目标规划路径。

## 2. 故障与恢复支路

- **未达成**：观察→stall→有限retry→失败分类→重规划或停车。LLM请求在飞与世界无进展目前混杂，见R09。
- **COUNTER/REJECT**：ConcernTool→Inbox→Detector→requestReplan→新计划；入队和消费两次都必须核验任务generation。
- **PAUSE**：Intent→PAUSED；当前实现停了RDD推进但未保证身体停下，自动复评计时有缺陷。owner暂停须受独立保护。
- **死亡**：NumenPlayer.tick→Companions.onDeath→DEATH事件→库存失效/LOST历史/台账/repair nudge；CompanionRegistry记录pendingDead；到延迟后respawnDead在主人附近生成；RDD SPAWN床偏好再尝试挪位。
- **重启**：TaskChain.fromJson将ACTIVE+RUNNING/STALLED归RECOVERING。暂停计时/死亡账等附属状态缺失或生命周期未清齐，不能只看TaskChain的JSON。
- **换目标/换世界**：回调ticket应失效，Inbox、计时、BODY记账、死亡记录也要有对应边界；当前清理不完整。

## 3. 状态的唯一解释权

| 状态/数据 | 真源 | 读者 |
|---|---|---|
| 当前primary/subtask状态 | TaskChain | Runtime、Detector、监测台、提示词 |
| 执行身体是否忙 | 宿主TaskSlot/CompanionTickDispatcher | 执行脑、只读监督快照 |
| 当前持有 | 服务端背包快照 | 验收与规划输入 |
| 世界基地/容器 | RddWorldFacts/WorldAssetObserver | 世界条件验收与监测 |
| 历史完成 | CompletedFactStore | 新链继承；不是当前仍持有物品证明 |
| 曾经丢失 | AssetHistory | 恢复线索；不是物品已消失证明 |
| 死亡事实 | CompanionRegistry+DEATH事件 | 恢复流程；不以即时HP单独判定 |
| 真使用的LLM | client initialised日志 + 请求观测 | 排错；全局toml不一定是同伴生效端点 |

时间约定：游戏tick通常20/s（50ms），单调墙钟用于网络期限，ItemEntity年龄用于掉落实体存活；三者不能互换。

## 4. 按症状查哪里

| 症状 | 先核证据 | 优先源码 |
|---|---|---|
| 一动不动 | 请求是否在飞、实际HTTP错误、身体槽、owner停止、链状态 | EntityAgentLoop / HttpLlmTransport / Detector |
| PAUSE后回不来 | pause原因、计时重复读是否归零、恢复入口是否可调用 | RddRuntime / handlePaused / TaskChain |
| 主人待命又自己动 | 身体槽有没有真正停止、上下文是否仍说必须执行、是否自动复评 | clearBody / renderStateContext / PauseController待建 |
| 说做完但世界没变 | condition类型、地点、数量、容器内容、证据source | conditionMatches / WorldFacts / Decomposer schema |
| 去村庄却无限等 | 是否错用villager作inventory asset_key；是否识别合法structure ID/tag | SubmitTool / WorldFactConditions / LocateStructure |
| 同一目标提交失败 | 是否继承了完成事实，bind后是否无条件start | CompletedFactStore / TaskChain构造 / SubmitTool |
| 重规划与旧计划一样 | soldierHint是否进实际prompt、旧计划条件值是否保留、过滤器删了什么 | requestReplan / renderPreviousPlan / PlanGuard |
| 老指令改了新任务 | 入队/消费generation、callback ticket、复用subtaskId | ConcernTool / Inbox / Detector / CallbackGuard |
| 走到门旁不传送 | nav是否tick、真实门体相交、门类型、维度变化 | UsePortalCompanionTask / PlayerNav / NumenPlayer生命周期 |
| 死亡后说掉落没了 | 死亡维度、区块是否tick、真实item/grave、历史时间估计 | DeathLedger / AssetHistory / RepairDispatch |
| 复活在主人旁边 | 宿主respawnDead选择的目标、个人床维度是否解析 | Companions / CompanionFactory / RddPlugin SPAWN |
| debug_kill成功但没死 | 回执success/alive、后续DEATH、pendingDead、新实体ID | RddDebugKillTool / NumenPlayer / Companions |
| 看不到资产 | asset_snapshot→adapter.payload→view、同伴过滤、时间新鲜度 | numen-adapter.js / rdd-view.js |
| 旧jar似乎没变 | 实际mods哈希、主jar vs classifier、资源在哪个模块 | run-mutation / config / build-jar / deploy |

## 5. 证据最小集合

每次验收保存runTag、时间、源码HEAD+未提交diff、实际部署jar SHA、配置端点脱敏摘要、请求/工具/世界结果同一时间段。关联字段建议worldId、companionId、goalGeneration、planRevision、primaryId、subtaskId、executionId、requestId、deathId。

事件存在只能说明那个分支发了日志：`task_negotiation`不等于规划器采纳；`body_submitted`不等于执行完成；`repair_task_dispatched`不等于捡回；`client initialised`不等于请求成功；`subtask_resumed`不证明前一条nudge导致恢复。

监测台资产表显示“24类”不是库存数量明细。建议加可展开物品名×件数、维度坐标、观测时间/LAZY历史标记，且任务为空也可看资产。

## 6. 维护约束

- 宿主生命周期/API、core执行、rdd-core状态机、plugins:rdd编排分模块改动。`numen_providers.json`位于ai、实际mods资源在api:neoforge；不能只构建core后宣称资源生效。
- 不删ToolDispatcher披露护栏。它确实返回失败结果，并非无声吞调用；应改善计划必需工具披露和受控恢复，不能盲重放身体工具。
- 不因“没有业务调用”就删存档枚举；先查存档迁移。不开的风险/依赖门是配置政策，不等于死代码。
- 玩家存档、模组配置、所有备份与资产事实不参加代码清理。
- 运行或配置探针不输出密钥；源码包只带白名单源码与脱敏文档。
- 冻结前需固定“支线先取备用还是先捡回”的政策，以用户最新验收意图为准，不靠旧注释裁决。

## 7. 整条链的通行性评价

正常路径已有可用骨架和历史运行证据；但“在简单目标上走通过”不能推导“每个异常出口可重入”。最薄弱的是状态切换跨越到身体控制、历史事实跨越到新任务、死亡跨越到重生/回收三处。下一轮应做少量针对这些接缝的测试，而不是继续增加相似record/getter测试数量。

建议复审顺序：暂停与旧协商隔离 → 提交事实继承 → 传送门动作闭环 → 死亡/重生证据闭环 → 监督观测真实性 → 小步抽类/清理。全部仍沿原架构推进，不开启第二批记忆/学习者。
