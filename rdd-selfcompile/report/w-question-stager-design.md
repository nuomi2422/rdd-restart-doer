## 一、要解决的问题

我们让 AI 改造一个 Minecraft 智能体（Numen）系统。踩过的坑是：

1. **AI「读过了就当走过」** —— 报告读起来完全像走完了流程，但整条证据链全跳。
2. **门禁查痕迹不查结果** —— 只看「今天有没有某个文件」，匹配到旧文件就放行。
3. **文档越写越多，AI 注意力被稀释** —— 39 份规则文档塞进上下文，关键信息沉中间。
4. **经验只写文档不进图谱** —— 下一个 AI 根本不会去翻那些文档，坑反复踩。
5. **AI 会「写个条子等拍板」来代替推进流程** —— 停工看起来像合规。

## 二、核心机制：把流程做成状态机 + 数据驱动

阶段定义放在一份 JSON 里（`stages.json`），改 JSON 就改流程，不用改代码：

```jsonc
{
  "loopTo": "plan",              // 轮回回到哪
  "stages": [{
    "id": "plan", "name": "计划统筹", "icon": "🗺️",
    "next": "implement",
    "read":  ["...必读 md...", ],      // ← 该阶段开工必读（薄索引，只给路径）
    "gate": { "docs": ["plan","arch"] }, // ← 不达标不许 next
    "ai":   ["...必做..."]              // ← 注入到 AI 上下文的指令
  }]
}
```

四个阶段：`①计划统筹 → ②编码实现 → ③游戏验证 → ④记录收口`，到④后轮回①且轮次+1。

**关键设计取舍**：每阶段的 `read[]` 只给**路径**，不给正文。AI 到那个阶段自己点进去读。
理由是「薄索引 + 点进去看」比「全塞进上下文」更能保住注意力。

## 三、门禁的三层，以及我们发现的弱点

| 门禁 | 查什么 | 能不能拦住 |
|---|---|---|
| flow-gate | 部署的 jar 的 sha == 构建产物 / 回滚点齐 / phase-*.json 阶段记录 | 靠实物，AI 编不出来 |
| loop-gate | 20 项九步流硬门（多数是「有没有留痕」） | 多数能被敷衍 |
| stager check | 本阶段该交的文档在不在、标记打没打 | 只查文件在不在 |

**我们给每项门禁打了性质标签**（不改判定，只加可见性）：

- 🔒 查实物 —— 验产物/哈希/事件流，AI 编不出来
- 📝 查痕迹 —— 只看「有没有写这段话」，写得出来就过
- 👤 人工 —— 机器判不了

实测占比：flow-gate **4:4**、loop-gate **5:15**。**越重的门禁，查痕迹占比越高。**
这个发现直接指出：光加门禁没用，得知道哪几条是自欺欺人。

**我们承认的弱点**：`stager check` 原本只看「文件在不在」，建个空壳 md + 打个标记就能过④。
已加「正文 < 500 字节点名」，但**只提示不拦**（判定级别没动）。

## 四、门禁性质分类的实测数据（我们自己踩出来的）

| 现象 | 含义 | 该怎么做 |
|---|---|---|
| 某项**每轮都秒过** | 它只在走过场 | 降级或删 |
| 某项**反复卡住** | 它在真拦 | 别削 |
| **AI 用敷衍内容就能过** | 判据太松 | 收紧判据（比降级更重要） |
| 🔒 查实物项**从没红过** | 可能没真在查 | 人工抽查确认它会红 |

**核心观点**：门禁不是越多越好，是**要看它到底在拦什么**。

## 五、经验库：从「只写不读」到读写闭环

我们有一个 memory MCP（知识图谱，存 JSONL）。踩过的坑：

- 早期图谱是空的 → 查了没用 → 更不查 → 永远空（正反馈坑）
- 后来灌到 50+ 条，**但没有任何规则叫 AI 去查** —— 变成「只写不读」的单向池子
- 检索是**子串匹配**，`search_nodes("死亡 台账 掉落 回收")` 这种长串返回空，
  害我们误判「图谱是空的」并把这个错误结论落盘了

修法：
1. **检索侧写进阶段指令**：每个阶段的 `ai[]` 开头强制 `memory_search_nodes("<关键词>")`，并给出各阶段关键词建议
2. **子串匹配的坑写进图谱本身**，让下一个人/AI 踩到时能查到

## 六、机器强制 > 文档要求

我们踩过的最深的一个坑：**「写进文档」不等于「改掉习惯」。**

同一个「起游戏会挂死」的教训：
- 写进了 12-进游戏验证工具集.md（AI 查得到）
- 也灌进了 memory 图谱（AI 查得到）
- **结果当天还是犯了第三次**

所以最后一道防线是**放在每次都会执行的指令位**（`stages.json` 的 `ai[]`），
而不是放在「要主动去查的文档」里。这是我们认为最重要的一条经验。

## 七、我们想请你们重点回答的问题

1. **门禁性质分类（🔒查实物/📝查痕迹）这个思路，在你们见过的工程实践里成立吗？**
   有没有更成熟的分类法（比如按「判定强度」分级、或引入对抗性测试）？

2. **「薄索引 + 点进去读」对抗上下文稀释** —— 这是有效的，还是只是把问题往后推了？
   我们担心的是：AI 可能根本不点进去读，或者读了但没真用。
   你们见过更可靠的做法吗？

3. **「只查痕迹的门禁」到底该保留还是该删？**
   我们的结论是「先不删，加标签观察几轮，看哪些每轮秒过再降级」。
   这个「先观察再动」的策略，还是应该现在就果断降级？

4. **状态机 + 数据驱动的流程定义（改 JSON 不改代码）** —— 这在你们那边是常规做法吗？
   有什么我们没想到的坑？

5. **门禁逼 AI 去修无关的工具 bug**（因为那些门禁红着会挡 next）——
   有没有更好的设计能让「该沉淀的东西」不被「清门禁」挤掉？

## 八、请直接说缺点

我们已经知道的：
- 8 个任务里 `wrap=0`（轮回机制从来没触发过）—— 因为从来没走到过④
- `stager check` 只查文件在不看内容
- 经验库曾经长期「只写不读」
- 我们自己两次改坏东西（给脚本加了个「答案必须比上次长」的判据，结果把某家模型挂死 400 秒）
