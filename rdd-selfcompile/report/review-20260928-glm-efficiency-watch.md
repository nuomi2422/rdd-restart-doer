## GLM 的 4 条意见 → 逐条核实与处置

### A) "消耗也是活动证据，任何 Δ≠0 都应重置；否则合成期/存箱期必误报" — **成立**
我的实现只在 `resNow > st.resTotal`（**涨**）时重置，掉下去只更新基线不重置计时。
而合成（9 raw_iron → 1 iron_ingot）、入箱都会让总件数**下降**，那是**正当活动**，
却会被我判成"没产出"并累计到 SLOW。**这是我判据的方向性错误。**
GLM 还指出 `res=491→235` 大概率是**入箱**（把东西存起来了）——看数据确实是骤降，符合入箱特征。
→ 处置：见下"本轮修/下批修"。

### B) "assets 已与进度脱钩（死信号），换成 done/子任务完成速率或里程碑推进速率" — **成立，我数据坐实**
实测：`asset=160` 从 22:46 到 22:52 一路不动，**而同期链条 r0→r5、物品种数 21→22、堆数 27→29**。
`assets` 是规划层的一个口径，跟真实进展脱钩。→ 应降级为辅助信息，不作为主判据。

### C) "只看绝对总量不够，应盯目标相关集合（含 raw_iron 等中间产物）的滚动窗口净增量" — **成立**
GLM 的反例很准：**刷泥土**会让总件数上涨 → 漏报"假装忙"；而**合法消耗**会让总数下降 → 误报。
两头都不对。真正的判据应是"**当前目标相关资源**在滚动窗口内有没有净增"。
`rdd_status` 里现成有 `condition.asset_key`（如 `minecraft:iron_ingot`）可用。

### D) 漏掉的三种卡住模式 — **全部成立，其中 D1 正是用户最早的原话（左右横跳）**
1. **乒乓循环**：A↔B 交替、各 <600s，所有计时器每次都被重置 → **四个信号全瞎**。
   修法：加**子任务 id 序列的重复/进入次数检测**（同一 id 短窗口内进入 ≥N 次即循环）。
2. **失败重试风暴**：FAIL 之后换个新 id，`failed_stuck` 立刻清零。
   **我自己的数据就是实例**：22:50:42 `fail=266s` 却 `sub_age=0s`、`done` 从 1 跳到 5。
   修法：改看**窗口内失败率**，而不是"失败持续时长"。
3. **成功但零目标进展**：刷简单可再生任务——`done/min` 正常、`res` 也在动，唯独**目标指标不动**。
   修法：只有**长窗口（如 30min）目标指标 Δ=0** 才抓得住。
