# 第一批源码深审与修复委托

审核日期：2026-09-30。基线：`95938d25`；当前 HEAD：`c3331d8e`，另含未提交修改和未跟踪新源码。本轮为独立源码审查，不调用 Codex、不改业务代码、不删除文件、不进游戏。runTag：`batch1-review-20260930`。

## 结论

**保留现有总体架构，但当前版本不适合直接固化成新红线。** 主干已经有明确分层：规划器负责生成计划，纯 JVM TaskChain 管状态，Detector 用世界证据验收，Numen 执行器操作身体。真正的问题是新增旁路缺少端到端契约：计时器、暂停、死亡台账、传送门和测试回执，各自看似成立，接起来却不一定能运行。

风险主要是“静默卡住、误判完成/丢失、旧请求影响新任务”，不是已经证明会普遍崩服。已有 `AbstractCompanionTask` 异常隔离、回调 generation ticket、原子存档方向应保留。本报告的 P1 表示阻塞固化的功能/控制缺陷，并不等于已证明损坏存档。未发现足以确认的 P0 崩服漏洞；不代表全仓无 P0。

此前声称的 845 个测试不是本轮重跑结果。单测数量不能替代以下集成路径。本轮使用 Read/Grep 静态追踪，并对已有编译产物运行独立 JVM 探针；没有调用真实付费模型或游戏。

## 一、必须先修的问题

路径均相对 `minecraft-numen/`，行号以审核时源码为准。

### R01 / P1：传送门 v2 没有驱动导航

- 证据：`core/common/.../task/interact/UsePortalCompanionTask.java:107-156,207-239`。
- `onTick()` 每次返回 `walkToward()`；后者每次新建 PlayerNav；包含 `nav.tick()` 的 `driveNav()` 从未调用。父类 `AbstractCompanionTask.java:131-146` 只调用子类 onTick，不替它跑导航。
- 后果：远处门无法通过这段导航到达，每 tick 重建对象，直到内部超时。测试只验证 record 字符串，完全覆盖不到。
- 修法：明确 SEARCH → APPROACH → ENTER → WAIT_TRANSFER → DONE/FAILED；只初始化一次导航，每 tick 驱动，换目标/结束前释放旧导航。
- 验收：假导航记录 tick 次数、初始化次数、失败清理；远处门逐步靠近。不得用描述文案测试替代动作测试。

### R02 / P1：传送门到达/超时/类型契约互相冲突

- `UsePortalCompanionTask.java:160-179` 把与目标相邻的空气格也算 inside；没有真正重叠门体就提前等待。end 门最终也只检查 NetherPortalBlock，必定走门丢失分支。
- `UsePortalTool.java:72-74` 把墙钟毫秒 `currentTimeMillis()+120000` 传给游戏 tick deadline；`api/common/.../task/TaskSlot.java:94` 却与 `level.getGameTime()` 比较。总 deadline 实际失效，并占同步槽等待结果。
- 进入与等待超时都从找到门时算；`insideSince` 不用于计算；`settleUntil` 仅在未调用的 driveNav 内设置。搜索到96格外门，却只给200 tick接近，不适配距离。
- 默认 TERRAFORM 无用户可控参数，与 goto 的显式地形许可约定不一致。工具描述还声称 USE 才传送、末地门双向、十块黑曜石可建所有门，均需修正。
- 修法：按目标门类型验证真实身体/门体相交，成功只认可预期维度变化；用游戏 tick 创建总预算并分阶段预算；远行按长任务派发，地形许可显式化；暂不支持 end 就从 schema 中撤下，不挂空能力。
- 验收：门旁但不在门内、脚位比门低10格、进入后等待、门消失、搜索空结果、取消清理、end支持或明确拒绝、无许可不改地形。

### R03 / P1：暂停复评计时读一次就被删除

- `rdd-core/.../core/RddRuntime.java:25-50`：`pausedTicks()` 用 `pausedAt.remove()`；Detector 每次检测调用它（`RddDetector.java:195`），而 markPaused 仅在接收 PAUSE 时调用（:528）。第一次检测就把起点拿走，此后永远返回0。
- 纳秒除以20,000,000得到每秒50个单位，而下游按20 tick/s换秒。即使修掉remove，“60秒”也会变成约24秒。
- 暂停状态持久化，计时却只存在 RddRuntime 内存；重启后无法续计时。
- JVM探针实测：`firstRead=50 secondRead=0`；存档恢复后 `status=PAUSED pausedTicks=0`。
- 修法：只读elapsed、不消费起点；注入统一clock；明确选择游戏tick或毫秒，并持久化暂停原因/时间/恢复条件；计时状态只能有一个所有者。
- 验收：连续读不变、59/60秒边界、重复暂停、重启、换级、换目标、旧计时清理。

### R04 / P1：暂停没有真正停止执行，自动恢复会违背主人待命

- `RddDetector.java:522` 的 `clearBody()` 只是 `RddPlugin.java:905-906` 删除 BODY 记账，**不是停止实际 TaskSlot**。
- `renderStateContext()`（RddPlugin:303-312）对 PAUSED 仍注入“current_task必须执行”；状态机暂停和执行脑指令冲突。
- `handlePaused()` 无监督开关/暂停原因门，条件满足或未来修好计时后会强制RUNNING。实际已出现主人要求待命的 PAUSE；不能把主人暂停当超时故障自动解除。
- PAUSED 状态下 COUNTER/REJECT 又被消费守卫挡住（Detector:513-516）。提示“上报改单”却没有可用消费路径。
- 修法：区分 OWNER_PAUSE、EXECUTOR_BLOCKED、WAIT_RESOURCE；主人暂停只能显式恢复；blocked可复评但不直接强制身体开工。通过宿主正式停止接口停止已有执行，保留单驾驶员。暂停状态上下文必须一致。
- 验收：长goto中暂停真正停止、主人暂停越过60秒不自启、条件变化仅通知/按策略恢复、暂停中协商可安全处理。

### R05 / P1：过时协商可能暂停/改写新任务

- `RddConcernTool.java:55-63` 只在入队时可选检查 taskId；空ID、无runtime会被接受。`RddDetector.java:508-528` 消费时不核对 `n.taskId()` 与当前subtask。
- `RddNegotiationInbox` 仅以companion UUID为键；`bindCurrent/removeCurrent/clearWorldState` 未清理该队列。生成二级ID还反复复用 `primaryId-r0`。
- `TaskNegotiation.parse()` :99-106 将未知kind降为ACCEPT；拼错PAUSE可清掉之前合法的待处理回执。
- 修法：信封必须含 worldId、goalGeneration、planRevision、subtaskId、messageId；消费时二次验证并返回明确拒绝；未知kind fail，不默认ACCEPT；只在安全转换或明确拒绝后ack。预算在接收转换成功后扣。
- 验收：PAUSE入队→新goal→下一tick，旧消息不得影响新链；COUNTER与ACCEPT并发；重复回执；空ID/未知kind拒绝。

### R06 / P1：完成事实继承与提交入口不兼容；不是简单“恢复矛盾”

- `TaskChain.java:46-64` 明确允许全阶段已继承时 primary=COMPLETED，二级仍PENDING（不伪造二级完成）。这在设计上有依据。
- `RddSubmitTool.java:47-58` 复用同伴ID构造目标，bind后无条件startCurrent；`RddPlugin.bindCurrent:358-359` 会注入旧完成事实。于是新链已经COMPLETED，startCurrent抛异常，工具报提交失败但已替换运行态并落盘。
- JVM探针已复现 `REBIND primary=COMPLETED subtask=PENDING; START rejected=current subtask cannot start`。
- 修法：提交结果分 ACCEPTED_RUNNING、ALREADY_SATISFIED、REJECTED；先校验再替换，不得失败后留下半提交。明确“继续同一目标”与“新开一次相同任务”的generation/继承策略。
- 不能把COMPLETED强行改ACTIVE，那会破坏完成事实红线。

### R07 / P1：死亡台账把估计过期断言为真实物品消失

- `RddDeathLedger.java:49-65,150-165` 按全局游戏时间差>=6000直接输出“ALL ... despawned / permanently gone / Do NOT go back”。
- 原版物品年龄随实体被tick增长；世界时间前进不意味着掉落物所在区块一直tick。还有拾取、火烧、keepInventory、墓碑模组等，不能凭时钟断言存在或消失。
- 台账缺worldId、dimension、实际掉落实体/物品关联、回收状态；`lostEntries`是失效库存条目数，不是本次真实掉落物数量。第二次死亡可能重复描述旧库存。
- 静态Map无生产clear调用、无落盘；重启丢账，同进程换世界可能串账。render只在死亡时调用，下一轮LLM看到的倒计时不更新。负gameTime文档说保护但实现没有。
- 修法：保留多次死亡结构记录，别砍成一条日志。分账“当前持有失效”与“可能可回收”；状态为OBSERVED_DROPS / RECOVERY_POSSIBLE / EXPIRY_UNCERTAIN / RECOVERED / CONFIRMED_LOST；计时只能作估计，缺实体证据不得宣布永久丢失。按世界+同伴持久化，动态注入双方规划上下文。
- 验收：多死16秒、区块卸载、世界仍运行但掉落区块不tick、重启、多世界、部分捡回、墓碑/keepInventory、熔岩销毁。

### R08 / P1：死亡支线目前主要是提示，不是闭合的任务生命周期

- `RddRepairDispatch.java:60-74` 建Task、覆盖LAST_REPAIR、发送nudge；未见生产调用 `onRepairSuccess/onRepairFailure`，未见其作为独立执行/验收状态推进。
- 主链继续有当前任务提示和stall监督，支线捡包与主线催工争抢执行脑；“生成repair_task_dispatched事件”不等于恢复支线完成。
- 修法：以小型RecoveryEpisode协调主链的保存点、恢复目标、期限估计、完成证据及恢复条件；它只编排，不绕过Numen执行身体。不要另造完整第二套TaskChain。
- 策略保留人工拍板：现行文档写先捡后取备用，而用户后来要求床旁拿备用再回收。做成风险/距离/剩余窗口策略；不得硬编码任何一种为永远正确。

### R09 / P1：卡死观测没有观测LLM，却报告“没有任何工具/请求”

- `RddStallWatcher.java:89-100,206-223` 只看身体currentTask、容器生产、位置和库存；无法区分LLM生成中、只读工具、压缩、对话、人工待命。
- 会在模型正常推理时注入催工，再走15秒stall和失败重试。提前5秒日志出现、后续又动了，**不能证明因果改善**。
- 执行脑已有 `EntityAgentLoop.java:543-545` 的工作状态（LLM/compaction/dispatcher/background），应由宿主以有界只读快照提供，不能让RDD读客户端私有变量或跨插件import。
- 修法：分开 transport timeout / response-without-action / body-no-progress / owner-pause；必须有活跃目标且预期执行，排除请求在飞/工具执行/合法等待；给催工预算并避免积压到下一轮。

### R10 / P1：床边复活跨维度链路不完整

- 真入口 `api/common/.../entity/Companions.java:267-299` 明确在主人当前维度和位置附近复活，延迟常量是5×20tick（:31）。不是世界出生点推测。
- RDD `recordSelfBedAnchor`（RddPlugin:632-640）只记同死亡维度的床；SPAWN处理（:157-175）只用BlockPos，在身体当前维度检查床，丢了床所属维度；跨维度死亡回基地无法保证。
- fallback还会在任何SPAWN（包括休眠恢复）读床后moveTo，与“仅死亡复活”注释冲突。
- 修法：宿主统一决定带维度的重生目标及原因，床验证失败才明确fallback到owner；RDD不再另做同坐标猜测式TP；覆盖死亡/休眠/首召唤/主人离线/床毁坏路径。
- 历史结论修正：和平模式不等于所有玩家攻击无效；库存未掉也不能证明未死亡；需要死亡事件、注册表pendingDead、新实体ID及keepInventory/墓碑/伤害取消证据。

### R11 / P2：debug_kill仍可能以成功信封报告失败

- `RddDebugKillTool.java:45-55` 无论died真假都TaskResult.ok。字符串写FAILED不等于机器判失败。
- `kill()`是否绕过该宿主所有伤害取消未被证明；注释不能当证据。
- 修法：未确认死亡则fail或明确pending，关联death事件确认；区分命令已提交、伤害被接受、死亡完成，不用立即HP独断。

### R12 / P2：供应商会话与配置边界

- `ai/.../numen_providers.json:31-46` 所有同伴/规划/压缩共用静态session `numen-minecraft`。应按真实会话隔离，而不是每请求随机或全局固定。
- 把API key写入游戏配置的旧脚本按全文件替换所有 `provider/model/base_url/api_key`，可能连STT段一起覆盖。审核阶段不读取输出秘密；实施者必须只改目标section并比较非目标section字节/字段。
- 不应把所有模型一律按相同协议/上下文参数处理；只保留验证过的模型条目，其余需逐项核实。

## 二、架构评价与拆分边界

### 应保留

1. TaskChain作为状态唯一写入点；完成事实独立于当前库存；跳过不伪造COMPLETED。
2. Stage-A / Stage-B懒展开及 RddGoalDriver 的展开所有权。
3. RddCallbackGuard在目标执行器内检查generation和原server的做法。新goal/换世界失效旧回调方向正确，不能清理掉。
4. AbstractCompanionTask对start/tick异常转换为任务失败，保护服务器主循环。
5. 单驾驶员：观察、规划和修复编排不直接并发夺身体。
6. 日志、世界事实、背包事实作为证据，**保留其区分**。

### 最小拆分方案（先修正确性，再抽类）

| 边界 | 拥有什么 | 不得拥有什么 |
|---|---|---|
| TaskChain（rdd-core） | 合法状态转换、当前计划revision、暂停元数据、不变量 | Minecraft、HTTP、文件I/O、nudge |
| RddRuntime | 调用门面、状态快照 | 第二套时钟/第二个状态仓库 |
| GoalDriver / ReplanCoordinator | 规划请求、预算、回调票据、计划替换 | 直接提交身体工具 |
| NegotiationCoordinator | 入队验证、消费二次校验、ack和暂停请求 | 用自然语言冒充权威状态 |
| PauseController | 原因分类、复评政策、显式恢复门 | 无视主人暂停的强制恢复 |
| RecoveryCoordinator | 死亡episode、主链checkpoint、回收证据、恢复条件 | 另一套泛化Planner/任意身体驱动 |
| ProgressObserver | 事实采样/分类，不直接判成功 | 把LLM延迟当无动作事实 |
| ConditionEvaluator | 持有/储存/放置/结构/维度等类型化验收 | 以资源类别数冒充件数或用错地点 |
| Detector | 按顺序调用上述组件的小型tick编排 | 持续新增所有业务分支 |
| api/common生命周期 | 真身停止、死亡、重生、世界代际 | RDD反向修改的第二份重生策略 |
| core/common工具 | 有界动作状态机和明确结果 | 主链状态、完成事实仓库 |

**不建议现在合并skipReasons/pauseReasons成抽象基类。** 两者语义不同，几行Map重复不是主要风险。PAUSED应保留；COOLDOWN/INVALIDATED暂未找到SubtaskStatus生产写入，可标deprecated，但必须先统计现有存档再决定迁移删除。不要按枚举数量评估质量。

**RddDeathLedger应保留意图、重构所有权和证据模型，不应砍成事件字段。** 用户明确需要跨多次死亡的账；删成一次性文本会丢掉核心需求。

## 四、给实施模型的执行顺序

每批一个目的，先保存当前diff和未跟踪源码，不擅自reset/clean。每批回归通过后再交回审核；本报告不授权自动commit/push。

1. **暂停与协商正确性**：R03-R06。加确定性时钟测试、主人暂停测试、旧回执换goal测试、已满足提交测试。禁止只把remove改get后就上线自动恢复。
2. **传送门闭环**：R01-R02。先用假导航/碰撞/时钟适配器测试阶段，再做允许时的真实双向传送验证。暂时明确限制nether功能，不能保留假end能力。
3. **死亡与重生**：R07-R08/R10-R11。在现有AssetHistory旁维护RecoveryEpisode，未知过期保持未知；床解析归宿主。用户已允许稍后处理的部分可排后，但保留“未验”标签。
4. **监督与模型请求**：R09/R12。真实request-in-flight与工具派发状态接入，单会话header；不通过取消披露护栏/自动重放有副作用工具解决上下文问题。
