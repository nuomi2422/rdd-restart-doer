## 二 · 逐条原文与修复

### ① P0：服务器线程同步等 LLM，plan-only 也会卡住游戏

**审稿原文**：
> `ExecuteToolPayload.handle()` 是服务器主线程入口；`LearnerReviewTool.onServerCall()` 第98行直接 `.join()`，
> LLM 超时设为120秒。`DEFERRED` 只是工具驻留策略，不是异步调度。
> **替代：**异步复盘，移除 `.join()`；完成后按原服务器/世界身份回调，过期回调失效。

**本轮修复**（`LearnerReviewTool.java`）：
- 改 `Thread.ofVirtual()` 后台线程执行复盘，主线程**立即**回执 `RUNNING` + `review_id`
- 世界代际校验：发起时捕获 `ServerLifecycleHooks.getCurrentServer()`，完成时校验
  `current == captured`，换档/重连后迟到回调**丢弃并 restore 队列**
- 模式抄已验证的 `AcExecuteTool`（后台线程 + 会话表 + 轮询）
- **实机验证**：调用后立即返回 `status=RUNNING`，游戏未卡

### ② P1：占位 memo_id 导致整批误删

**审稿原文**：
> 批量解析调用 `Verdict.parse("?", ...)`；`Verdict.parse` 使用传入 ID，根本不读取 JSON 的 `memo_id`。
> 随后只检查判定列表非空，就 `commitDrain(taken)` 删除整批。
> **替代：**严格校验输入/输出 ID 一一对应、无重复、无陌生 ID；只确认已有持久判定的条目。

**本轮修复**：
- `Verdict.parse` **改为从 JSON 读 `memo_id`**；缺失且无合法 fallback 时返回 `null`（不产出判定）
- `LearnerReviewer.parseAll` 增加：陌生 id 丢弃、重复 id 只认第一次
- `LearnerReviewTool.completeOnServer` **只 commit 拿到判定的条目**，其余 `restore`
- 防御：非 `m-` 前缀的 id 不流入监测台/下游
- **单测**：`readsMemoIdFromJson` / `rejectsVerdictWithoutMemoId` / `rejectsUnknownAction`
- **实机验证**：gpt 实例 2 条备忘录 → 2 条判定，`memo_id` 与 `noted` 事件**逐条对应**，`committed=2 restored=0`

### ③ P1：携带器把关键词当事实

**审稿原文**：
> `armor=none` 仍被认定有护甲；`hostile=false` 仍算附近有敌人。
> 血量解析在遇到 `:` 时没有跳过分隔符，普通 `"hp":12` 解析失败；`12/20` 分支的截取位置同样有误。
> **替代：**在 API 层定义带时间、对象身份和明确未知值的快照 DTO，宿主采集、携带器纯计算。

**本轮修复（前半）**：
- 弃用 `contains`，改解析 `key=value` / `"key":value`，并识别否定值（none/no/false/0/空/无）
- 修正分隔符跳过与 `N/20` 匹配（改用正则 `(\d{1,3})\s*/\s*\d{1,3}`）
- **单测锁死**：`carrierDoesNotTreatArmorNoneAsEquipped`（armor=none → `护甲=无` + 携带「护甲获取类工具」）、
  `carrierRecognisesRealArmor`、`carrierGradesHealth`、`carrierHandlesJsonStyleSnapshot`
- **实机验证**：`指向=HOSTILE_NEARBY 护甲=无 血量=LOW(6)`（快照是 `armor=none`，判对）

**未做（审稿要求的后半）**：
- 「带时间/对象身份的快照 DTO」= 架构级（要动宿主采集），本轮未做。v1 仍用 AI 自报的 snapshot 文本，
  **该文本的可信度等于干活 AI 的诚实度**，属已知局限，已写入 28 号文档与测试日志。
- 「结果驱动记忆检索并携带实际条目」= v1 携带器只产出**类别字符串**（战斗相关经验/护甲获取类工具…），
  **没有真的去检索并携带具体经验条目**。这是本轮最明确的功能缺口。

### ④ 队列实现的并发与崩溃（审稿指出 3 处）

| 审稿指出 | 本轮处理 |
|---|---|
| `readAll()` 把 IO/解析错误当空队列，后续 `append` 会**覆盖原文件**（明确的数据丢失路径） | ✅ 读失败改抛，坏文件原地保留；单测 `corruptQueueThrowsAndDoesNotOverwrite` 断言原文件一字未改 |
| `restore` 未检查 64 条上限 | ✅ 补上限；单测 `restoreDoesNotExceedCapacity` |
| 固定 `.tmp` 文件名会冲突 | ✅ tmp 名带 pid + 纳秒 |
| 60 条 × 长文本全量重写无长度上限 | ✅ 加 `MAX_FIELD_CHARS=4000` 字段上限 |
| 文件名 `.jsonl` 但内容是 JSON 数组（误导） | ✅ 改名 `.json` |
| 「commit 后、结果交付前崩溃」会丢判定 | ⚠️ **未完全解决**：v1 判定只在内存/监测台，崩溃后备忘录已删判定未留。已记入未完成项 |
| 锁不覆盖整次复盘，两个消费者可 drain 到同一批 | ⚠️ v1 单玩家场景不会并发；已记入未完成项 |

### ⑤ plan-only 是否违背用户意图

**审稿原文**：
> plan-only **可以作为临时隔离阶段，但不能算完成用户要求**；用 RL-9 禁止学习者写经验，属于过度降级。
> 防止学习者另起身体执行链是对的；把所有动作退回「干活 AI 自己决定」不对。
> 单驾驶员限制的是身体控制权，学习者可以自己判断、写经验，并向唯一执行器提交 AC 请求。

**审稿给的正确做法**（本轮**未实现**，列入第二阶段）：
```java
// api/common/.../api/NumenApi.java
CompletionStage<String> callTool(UUID companionId, String callId, String toolName,
                                 JsonObject args, InvocationContext context);
```
- `InvocationContext` 由宿主签发/校验，携带来源、执行会话、幂等键和**身体控制租约**；不能只信调用者填一个 `"learner"` 字符串
- 写经验必须产出 `type/title/description` 等结构化参数（`ExperienceLearnTool.java:60` 要求），现在只有 `experienceDraft` 字符串不足以直接执行
- 门面返回的是工具回执，**不自动代表行动完成**；`ac_execute` 返回 `RUNNING`，要保存 `execution_id` 跟踪终态（`AcExecuteTool.java:99`）

**本轮立场**：接受该判定。v1 是隔离阶段，**不声称完成用户原始要求**，测试日志已明写。

### ⑥ 全局锁该插在哪一层

**审稿列出的「自动提交工具/指令」真实出口**：

| 出口 | 行为与证据 |
|---|---|
| RDD 自动提交/重试 | `maybeSubmit→submit`、`resubmit→submit` → `tool.onServerCall`（`RddBodyDispatcher.java:36,99`） |
| AC 启动 | 后台 `executor.execute(...)`（`AcExecuteTool.java:96`） |
| AC 恢复 | `executor.resume(...)`（`AcResumeTool.java:65`） |
| AC 每步调用 | `host.invoke→tool.invoke`（`NumenToolBridge.java:56`、`NumenHostAdapter.java:37`） |
| 网络工具入口 | 校验后直接 `tool.onServerCall`（`ExecuteToolPayload.java:154`） |
| 身体任务安装 | `put` 同步槽 / 当前任务槽（`TaskDispatch.java:52,83`） |

**审稿建议的插入点**：
1. 把 `ExecuteToolPayload.handleCompanion():154` 和 `RddBodyDispatcher.dispatch():99` 汇入宿主 `ToolInvocationService`；AC 的 `NumenHostAdapter.invoke()` 也走它，传递同一执行会话
2. `TaskDispatch.runSync/setTask` 安装任务前校验租约；`TaskSlot.put()` 作最终防线（它会停旧任务并标取消，`TaskSlot.java:68`）
3. 仲裁键 = **服务器/世界实例 + companion UUID**；同一 AC 子步骤继承控制权，另一驾驶来源排队或明确拒绝；不同同伴不必互锁
4. 租约持续到身体执行真正结束，**不能收到 `RUNNING` 回执就释放**；超时撤销后用代际标识拒绝迟到指令；只读查询/复盘/写经验**不占**身体租约

**为什么另两层不够**：`NumenTool.invoke()` 可被覆写且 RDD 直接绕过它；插件各自的锁彼此不共享；单锁网络入口挡不住 RDD。
**Java 互斥锁只让提交依次发生**，仍会出现 A 提交、B 替换、A 再替换。

**本轮处理**：v1 不执行 → 无对象可锁 → **按文档 §5 推迟**（装「锁住空气的锁」= 假红线）。第二阶段按上表实装。
